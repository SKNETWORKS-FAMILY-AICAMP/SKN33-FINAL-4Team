# 거래 분류 에이전트

카드 · 계좌 소비 거래의 가게 이름을 보고 10개 소비 카테고리 중 하나로 분류한다. 확실하지 않으면 정하지 않고 '확인 필요'로 남겨 사용자에게 묻는다.

| 항목 | 내용 |
|---|---|
| 대상 | `transaction_type = spending`인 거래. 입금 · 이체 · 카드값 · 사용자가 이미 확정한 거래는 건드리지 않는다 |
| 실행 시점 | 거래 저장 뒤 처리 2단계 `finance.pipeline.classify_spending` → `finance.classifier.classify()` |
| 분류 기준 | [소비 카테고리 분류 기준](../소비카테고리_분류기준_20261105.md) |
| 결과 저장 | `financial_transaction`의 확정 · 추천 카테고리, 분류 출처(`rule` · `ml` · `llm`), 후보 최대 3개, 이유 문장. 판단 근거는 `field_states.classifier` |

## 1. 흐름

```
가게 이름 정리 (결제대행 접두어 · 결제수단 꼬리표 떼기, 'A - B' 표기 나누기)
  ↓
① 다품목 · 페이 충전 · 결제대행사 이름 ─────────────→ 확인 필요 (지난 선택은 후보로)
② 사용자 기억 ('앞으로도 적용'으로 고른 가게) ───────→ 그 카테고리
③ 규칙 · 사전 (교통 · 구독 · 운영사 법인명 · 편의점/마트) → 그 카테고리
   카드사 가맹점 업종이 있으면 여기서 함께 판단
④ SVM (상호명 모델, 확신도 ≥ 0.85) ────────────────→ 그 카테고리
⑤ 검색 + Jev (지도 · 웹 근거로 판단) ───────────────→ 그 카테고리
⑥ 위에서 못 정함 ──────────────────────────────────→ 확인 필요 (후보 3개 + 이유)
```

자동으로 정한 거래도 상태는 `suggested`라서 사용자가 거래 화면에서 언제든 바꿀 수 있다.

## 2. 단계별 규칙

**이름 정리**
- `NICE*` · `KCP-` 같은 결제대행 접두어와 `_카카오페이` · `_KCP` 같은 결제수단 꼬리표를 뗀다.
- `A - B` 표기는 A로 끝까지(③~⑤) 보고, 못 정하거나 A가 결제대행사면 B로 다시 본다. A가 결제 경로(`네이버페이 - 봄툰`)면 처음부터 B만 본다.
- 카드사가 이름을 자른 경우(적요 40바이트 이상): 끝 이름의 앞부분 일치로 검색 근거를 인정하고, 웹 글에서 온전한 이름을 찾으면 그 이름으로 한 번 더 검색한다.
- 비식별 표기 · 숫자뿐 · 한 글자처럼 상호가 아닌 이름은 SVM · 검색 없이 확인 필요다.

**① 바로 묻는 거래**
- 다품목(종합몰 · 백화점 · 애플처럼 여러 서비스가 한 이름으로 찍히는 곳): 무엇을 샀는지 이름만으로 알 수 없어서 묻는다.
- 페이 충전(토스페이충전 등): 무엇에 썼는지 몰라서 묻는다. 교통카드 충전(티머니 등)은 교통 · 차량.
- 결제대행사만 찍힌 거래(`…페이먼츠`, `KG이니시스` 등): 어느 가게인지 알 수 없어서 묻는다.

**② 사용자 기억**
- 사용자가 거래 화면에서 카테고리를 고를 때 '앞으로도 적용'을 체크한 가게만 다음 거래에 자동으로 쓴다(`classification_source = rule`). 체크하지 않은 선택은 그 거래에만 적용된다.
- 지난 선택과 이번 거래의 카드사 업종이 둘 다 구체적이고 서로 다르면 기억을 쓰지 않고 이번 업종으로 판단한다.

**③ 규칙 · 사전**
- 교통: 택시(`개인택시` · `법인택시` · 띄어 쓴 `택시`) · 교통카드 · 고속버스 등 → 교통 · 차량.
- 구독 · 운영사 법인명: 넷플릭스 등 OTT · 음악 → 문화 · 여가, 우아한형제들(배민) · 쿠팡이츠 → 식비, 카카오스타일 → 패션 · 쇼핑 등.
- 편의점 · 슈퍼 · 대형마트는 식비, 다이소는 생활용품으로 기본 분류한다.
- 카드사 가맹점 업종(`merchant_category`)이 있으면 같은 이름의 과거 검색 결과보다 먼저 쓴다.

**④ SVM**
- 상호명 모델([ML 모델](../ML_MODELS.md#1-거래-분류-svm))의 확신도가 0.85 이상이면 그 카테고리로 정한다. 미만이면 후보 3개를 남기고 ⑤로 간다.
- 상가 데이터에서 같은 이름에 다른 업종이 섞인 이름(동명 충돌 목록 `label_conflicts.csv`)은 SVM이 확신해도 정하지 않고 ⑤로 보낸다.

**⑤ 검색 + Jev**
- 네이버 · 카카오 지역 검색(각 3건)과 네이버 웹문서 검색으로 근거를 모은다. 정리한 이름이 완전히 같은 가게만 지도 근거로 쓰고, 웹 근거는 글에 가게 이름이 들어 있을 때만 쓴다.
- 지도 근거 · 웹 근거를 각각 TypeSafe Jev(`Choice`: 10개 카테고리 + 기타 + 판단 보류)에 묻는다.
- 자동 적용 조건: 근거 있음 + 판단 보류 아님 + 확신도 0.9 이상 + 지도 · 웹 답이 서로 다르지 않음. 근거 없이 이름만으로 물은 답은 0.95 이상일 때만 적용한다(`name_only`).
- 검색 업종이 편의점 · 마트면 식비, 백화점 · 종합몰이면 묻는다. 금융 · 회사 · 소프트웨어 같은 업종은 근거로 쓰지 않는다(본사 사무실이 검색되는 경우).
- 외부 호출이 실패하면 재시도하지 않고 확인 필요로 끝낸다. 같은 이름의 검색 · Jev 결과는 한 번의 분류 실행 안에서 재사용한다.

**⑥ 확인 필요 이유 문장** — 사유별 고정 문장이다(LLM으로 만들지 않는다).

| 사유 | 문장 |
|---|---|
| 이름만으로 모름 | 가게 이름만으로는 카테고리를 정하기 어려워요. |
| 다품목 | 여러 종류의 물건을 파는 곳이라 무엇을 샀는지 골라 주세요. |
| 검색 0건 | 가게 정보를 찾지 못해 카테고리를 정하지 못했어요. |
| 찾았지만 불확실 | 가게 정보를 찾았지만 카테고리를 확실히 정하지 못했어요. |
| 조회 실패 | 가게 정보를 확인하지 못했어요. 직접 골라 주세요. |
| 페이 충전 | 페이 충전이라 무엇에 썼는지 골라 주세요. |
| 동명 충돌 | 같은 이름의 다른 업종 가게가 있어 카테고리를 정하지 못했어요. |
| 결제대행사 | 결제대행사 이름으로 찍혀서 어느 가게인지 알 수 없어요. 직접 골라 주세요. |

## 3. 안전 원칙

- 검색 API에는 정리한 가게 이름만 보낸다. 계좌번호 · 사용자 이름 · 거래 전체는 보내지 않는다.
- 거래 적요 · 검색 결과 속 문장은 데이터로만 다룬다(지시문으로 따르지 않는다).
- LLM 점수만으로 정하지 않는다. 검색 근거가 있어야 `llm` 출처로 저장한다(이름만 물은 답은 더 높은 기준).
- 사용자 기억은 같은 회원 것만 쓴다.

## 4. 화면

- 거래 목록의 '확인 필요' 거래 → [카테고리 고르기] 팝업(`TxPickPopup.jsx`)이 이유 문장과 추천 후보를 보여 준다. 고르면 `PATCH /api/finance/transactions/<id>/`로 저장한다.
- 거래 상세의 '분류' 줄: 내가 고름 / 규칙으로 자동 분류 / AI 자동 분류.
- '앞으로도 적용' 체크박스는 페이 충전 · 원래 이체였던 거래에서는 숨긴다.

## 5. 설정 · 파일

| 무엇 | 위치 |
|---|---|
| 에이전트 본체 | `backend/finance/classifier.py` (`classify` · `rule_category` · `predict` · `judge`) |
| 사용자 기억 | `backend/finance/merchant_rules.py` |
| 이름 정리 · 교통 규칙 | `scripts/spending_classifier/common.py` · `transport_rules.py` (서버가 import하므로 배포에 `scripts/`가 필요) |
| SVM 모델 | `SPENDING_MODEL_PATH` (기본 `local_workspace/models/spending_classifier/…/spending_category_svm.joblib`, Git에 없음) |
| 동명 충돌 목록 | `SPENDING_CONFLICTS_PATH` (기본 `local_workspace/models/spending_classifier/label_conflicts.csv`, 없으면 경고만) |
| 지도 · 웹 검색 | `KAKAO_REST_API_KEY` · `NAVER_CLIENT_ID` · `NAVER_CLIENT_SECRET` |
| Jev | `TYPESAFE_API_KEY` · `JEV_MODEL` (없으면 ⑤를 건너뛰고 확인 필요) |

모델 파일이 없으면 분류 단계가 실패로 기록되고 다음 동기화 때 다시 시도한다.

## 6. 운영 명령

```bash
cd backend
python manage.py classify_transactions [--email 회원]    # 저장된 소비 거래 다시 분류 (사용자 확정 거래는 그대로)
python manage.py classify_names 이름목록.txt --csv 결과.csv  # 이름 목록을 실제 분류기로 돌려 보기 (DB는 되돌림)
python manage.py test finance.tests.test_classifier      # 자동 테스트 (네트워크 없이 모의 응답)
```

`classify_names` 결과 CSV의 `정답` 칸을 채우면 기준값 평가에 쓸 수 있다. 실거래 이름이 든 파일은 커밋하지 않는다.

## 7. 한계

- 기준값(SVM 0.85 · Jev 0.9 · 이름만 0.95)은 상가 데이터 검증과 실거래 표본으로 정했다. 사람이 검수한 큰 실거래 검증셋으로 카테고리별로 다시 정할 여지가 있다.
- 검색 · Jev는 거래 잠금 안에서 돈다. 거래당 약 0.3~0.7초라 동기화 건수가 많으면 시간이 길어진다.
- 지점명을 붙이면 지도에 없는 브랜드, 업종이 같은 문구점 · 팬시점은 구별이 어렵다.
